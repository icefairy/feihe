## 一、语音方向（Android）

### 1. 中文标点小模型（用户点名要记的第一条）

**要做的事**：自己训一个字符级的 CNN-BiLSTM 标点恢复模型，塞进输入法，替代现在
`VoicePunctuator` 那个「只补句末一个字符」的启发式。

**为什么现在不做**：现成的中文标点 ONNX 模型**最小是 155 MiB**（BERT-base 系），
比 ASR 模型还大一倍；`sherpa-onnx` 的 CT-Transformer 是 280.7 MiB。79 MB ASR + 155 MB
标点 = 234 MB，和直接用 SenseVoice 一个量级，没有意义。

**可行的路子（已调研，别重查）**：
- 架构照 `frankyoujian/Edge-Punct-Casing` 那条走——**CNN + BiLSTM**，不是 BERT。
  它英文版是 28.2 MiB，证明这个量级可行。
- 中文能做得更小：字符表（~7000 字）而不是 8k+ 的 BPE 词表。
  嵌入 7000×64 + 卷积 + 2 层 BiLSTM + 5 分类头（无 / ，/ 。/ ？/ ！），
  参数 50–80 万 → **fp32 2–3 MiB，int8 后不到 1 MiB**。
- **标点语料几乎是白送的**：任何正常中文文本去掉标点就是一对训练数据。这和语音
  识别完全不同（那个要音频+转写对齐，基本拿不到）。

**前置条件**：
1. 装 PyTorch（CPU 版约 2.5 GB，走阿里云 pypi 应该能过）。本机目前
   **torch / onnxruntime / onnx 一个都没装**。
2. 拉几 MB 干净中文语料（hf-mirror 663 KB/s 可用）。
3. **一份评测集**——几十条真实语音识别结果，人工标好该在哪儿加标点。
   没有它，训完也不知道是变好还是变坏。

**触发时机**：M4 上线、真实用了一段时间、觉得「没逗号实在难受」的时候。
先攒样本，再训模型——顺序反了就是闭着眼调参。

### 2. ASR 纠错

**要做的事**：修识别错字（同音错、专有名词错）。

**坏消息（已查，别重试）**：`sherpa-onnx` 的热词/上下文偏置走 `modified_beam_search`，
那是 **transducer** 的解码路径；我们用的 paraformer 是 CIF + 注意力解码，
**没有这个入口**。所以纠错只能做后处理，两条路：

1. 用飞鹤自己的 98k 词库做「低频词 → 同音高频词」替换。零体积零训练，但容易误伤专名。
2. 4 MB 量级的字符级 reranker（例如 `chinese-ime-lm` 那个，Apache-2.0）。
   **必须有评测集**。

**触发时机**：同上，先有评测集。

### 3. SenseVoice 升级路径（可选）

如果将来嫌 paraformer 没标点，升级方式是**下载** 228 MB 的 SenseVoice（不进安装包）。
实测数据都还在 `docs/Android-方案.md` §4.2.3：
ModelScope 4.89 MB/s、支持 Range、`X-Linked-ETag` 就是 SHA256、GitHub 完全不通。

**要做的前置**：在 ModelScope 建**自己的**仓库把那 238 MB 传上去。
现在用的社区转存（`poloniumrock/SenseVoiceSmallOnnx`）随时可能被作者删掉，
不能当产品的唯一下载源。

      `tools/gen_next.py` 以后可以加一个「读本地纯文本语料统计」的模式，
      等有语料文件时一条命令重生成。
- [ ] **词频半衰期**：要改 `freq.txt` 的行格式（加时间戳）+ 老文件迁移。
      收益是「三个月前常打的词不再压着我」。不急。
- [ ] **候选来源标记**（qingjian 清单 #9）：标出这个词来自模糊音/纠错/自定义短语。
      纠错那批候选现在没有任何视觉区分，用户不知道自己在选猜出来的词。
- [ ] **分词加权 DP**（qingjian 清单 #2）：**建议不做**。没有回放语料，
      改权重就是凭感觉调参，坏了也说不清坏在哪。
- [x] ~~**「安装目录一堆 txt 合并成一个 SQLite」**~~：**评估后不做**，理由记在这里。

      用户的原话是「好多 txt 会不会显得不错专业？适合都放到 sqlite 里做成一个文件？」。
      先把安装目录里到底有什么摆清楚（本机 0.3.14 的实测）：

      | 文件 | 大小 | 谁写 | 人该不该看 |
      |---|---|---|---|
      | `feihe.dll` / `feihe32.dll` | 6.3M + 6.4M | 安装包 | 否 |
      | `user.bin` | 4.8M | 「编译个人词库」 | 否（`user_dict.txt` 的产物） |
      | `user_dict.txt` | 1.6M | 导入 / 手改 | **是**，这是唯一「用户的源文件」 |
      | `freq.txt` | 39K | 调频 | 是（可删可改） |
      | `next.txt` | 8K | 联想 | 是（可删） |
      | `phrases.txt` / `pinned.txt` | 7K + 1K | 自定义短语 / 置顶 | 是 |
      | `config.ini` | <1K | 设置窗 | 是 |
      | `backup-*.bak` | 每份 4~6M | 安装器改名兜底 | 否（装几次就几份，**该清**） |
      | `feihe.log` | ≤256K | 诊断 | 排查时看 |

      结论分三条：

      1. **不该合并**。这些不是同一类东西：两个 DLL 是代码，`user.bin` 是编译产物，
         剩下五个是**用户的可读源文件**（手改、导出、删掉即清空都写在帮助里）。
         塞进一个 `.db` 之后，「删掉 next.txt 即清空联想」这种零成本操作没了，
         换成「装个 sqlite3 命令行改 BLOB」——是退步。
      2. **不需要 SQLite**。词库的正经形态已经是二进制的（FHDB：偏移表 + 字节池，
         构建期算好、运行时二分、零解析、mmap 共享物理页）。再套一层 SQLite，等于
         在已经最优的读路径上再加一次页缓存和一次 `sqlite3_step`，**只会更慢更大**。
         SQLite 解决的是「随机的增删改查」，而这里的写是「整表重写一次」，用不上。
      3. **「显得专业」恰恰相反**。用户看到一堆 txt 会想「我能改」；看到一个不透明的
         `.db` 会想「千万别碰，坏了不知道怎么办」。搜狗/微软那套不透明的词库文件，
         用户评价从来不是「专业」，是「卸不干净」。

      **真正该收拾的是 `backup-*.bak`**：本机 8 份、36M，是安装器「改名兜底」的残留
      （见 `installer/feihe.nsi` 的 `MakeBackupName`）。安装器现在只在成功替换后
      `Delete "$0\backup-*.bak"`，替换失败时留着给回滚——但成功很多次之后仍可能剩几份。
      这个另开一条，见下面。

- [x] ~~**安装后清掉残留的 `backup-*.bak`**~~：2026-11-06 完成。`CopyOrReplace`
      只在**本次走到改名替换**时才清 `backup-*.bak`；本次首拷就直接成功（DLL 没被
      映射，最常见的情况）那条 `done` 分支根本不执行，于是装 N 次攒 N 份。
      现在 `Section "主程序"` 一进来、在第一次 `CopyOrReplace` **之前**就无条件
      `Delete "$INSTDIR\backup-*.bak"`：此刻本次的文件还没落地，目录里的 bak 一定
      是更早版本的残留，删了不影响本次回滚（本次失败时 `MakeBackupName` 会另起新名）。
      删不掉（仍被映射）就留到下次，不拦安装。

- [x] ~~**自动整句**~~：打 `vhsjli` 现在出「张三李」（切段 → 每段取第一名拼起来），
      打 `nihaoshijie` 出「你好世界」。分段规则从 `textservice` 搬进了

      在两端切出不同的词，没人查得到原因。只在**整码查不到候选**时才出整句
      （整词优先），一次按键最多几毫秒。
- [x] ~~**逐段选择**~~：2026-11-05 完成。**手势决定：点段换词，不做左右移段** ——
      候选条画成 `[张三][李]` 一排 chip，点哪段展开哪段的候选，选完自动回到 chip 视图，
      空格/回车/标点整句上屏。没有游标，直接绕开「单行候选条左右移段很别扭」。
      分段规则继续用 `feihe_core::segment::plan`（`dict::segment_candidates`），
      Kotlin 里绝不重写切分；「这一条候选是不是自动整句」由 `lookup_input` 的
      `LookupResult.segments` 显式带出，壳不靠「候选只有一条」去猜。
      纯状态机 `SegmentState` 9 项 JVM 单测，core 侧 8 项喂假词库单测。

一个容易踩的坑，已经踩过一次：**分段时的「这一段有没有词」不能用 `dict::any`**
（它是前缀探测）。`any("vhsjli")` 会因为词库里有「张三李四」（码 `vhsjlisj` 以它开头）
而返回真，于是 DP 以为整串是一个词，切分退化成逐字，整句变「长三裏」。
现在用 `dict::any_aligned` / `first_aligned`（字数必须等于音节数），
推导和代价写在 `dict.rs` 的 `ALIGN_SCAN` 注释里。

### A4. 剪贴板钩子（挡着 `fancha` 进 core）

`fancha::from_clipboard` 直接调 `clipboard::text()`（Windows 剪贴板 API）。要让它进
core，得开一个 `set_clipboard_reader(fn() -> Option<String>)` 的钩子——和
`config::set_fullscreen_probe` 同一个套路。
